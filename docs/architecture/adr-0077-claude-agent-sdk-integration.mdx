# 77. Claude Agent SDK Integration

Date: 2025-12

## Status

Accepted

## Category

Core Architecture & Agent Frameworks

## Context

The MCP Server LangGraph project has primarily used LangGraph for agent orchestration, with LiteLLM providing multi-provider LLM access. While this approach offers flexibility across LLM providers, it doesn't fully leverage Claude-specific capabilities and best practices when using Anthropic's models.

### Current Limitations

1. **Generic Tool Calling**: LiteLLM provides standardized tool calling, but doesn't optimize for Claude's specific tool use patterns
2. **Streaming Responses**: Custom streaming implementation doesn't leverage Claude SDK's built-in streaming primitives
3. **Error Handling**: Manual retry logic doesn't utilize Claude SDK's sophisticated error recovery
4. **Agent Patterns**: Missing Claude-specific agent patterns documented in Anthropic's engineering guides
5. **Configuration**: Manual configuration of Claude-specific parameters (temperature, tokens, etc.)

### Anthropic's Recommendations

From [Building Agents with the Claude Agent SDK](https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk):

- Use Claude SDK for Claude-specific optimizations
- Leverage SDK's tool calling abstractions
- Utilize built-in streaming response handlers
- Implement retry logic with exponential backoff
- Follow agentic loop patterns (gather, act, verify, repeat)

### Requirements

1. **Maintain Multi-Provider Support**: Continue supporting OpenAI, Google, Azure via LiteLLM
2. **Claude Optimization**: Use Claude SDK when Claude models are selected
3. **Unified Interface**: Abstract SDK differences behind consistent interface
4. **Configuration**: Integrate SDK configuration via existing LiteLLM provider abstraction
5. **Backward Compatibility**: No breaking changes to existing agent APIs

## Decision

We will integrate the **Claude Agent SDK** alongside LangGraph, using it selectively when Claude models are chosen while maintaining LiteLLM for multi-provider support.

#### 3. Streaming Response Handling

**Claude SDK Streaming**:

```python
async def stream_response(
    messages: list[dict[str, Any]]
) -> AsyncIterator[str]:
    """Stream Claude responses using SDK primitives."""

    async with claude_agent.stream(messages) as stream:
        async for event in stream:
            if event.type == "content_block_delta":
                # SDK handles delta formatting
                yield event.delta.text
            elif event.type == "message_stop":
                # SDK signals completion
                break
```

**SDK Features**:
- Automatic reconnection on network errors
- Delta accumulation and formatting
- Event type discrimination (content, tool_use, etc.)
- Graceful error handling

#### 4. Error Handling and Retries

**Claude SDK Retry Logic**:

```python
from anthropic import (
    APIError,
    APIConnectionError,
    RateLimitError,
    APITimeoutError
)

class ClaudeAgentWrapper:
    def _setup_retry_logic(self):
        """Configure exponential backoff retry logic."""
        self.retry_config = {
            "max_attempts": self.config.retry_max_attempts,
            "backoff_factor": self.config.retry_backoff_factor,
            "retryable_errors": [
                APIConnectionError,
                RateLimitError,
                APITimeoutError
            ]
        }

    async def _invoke_with_retry(self, **kwargs) -> dict[str, Any]:
        """Invoke with exponential backoff retry."""
        for attempt in range(self.retry_config["max_attempts"]):
            try:
                return await self.client.messages.create(**kwargs)
            except tuple(self.retry_config["retryable_errors"]) as e:
                if attempt == self.retry_config["max_attempts"] - 1:
                    raise
                await self._backoff(attempt)

    async def _backoff(self, attempt: int):
        """Exponential backoff with jitter."""
        delay = (
            self.retry_config["backoff_factor"] ** attempt
            + random.uniform(0, 1)  # jitter
        )
        await asyncio.sleep(delay)
```

**SDK Error Types**:
- `APIError`: Base error for all API errors
- `APIConnectionError`: Network connectivity issues
- `RateLimitError`: Rate limit exceeded
- `APITimeoutError`: Request timeout
- `AuthenticationError`: Invalid API key

```python
class LLMFactory:
    """Factory for creating LLM instances with provider abstraction."""

    def create_llm(self, provider: str, model: str) -> BaseLLM:
        """Create LLM instance based on provider."""

        if provider == "anthropic" and model.startswith("claude"):
            # Use Claude SDK for Claude models
            config = ClaudeAgentConfig(
                model=model,
                max_tokens=self._get_config("max_tokens"),
                temperature=self._get_config("temperature"),
                api_key=self._get_api_key("anthropic")
            )
            return ClaudeAgentWrapper(config)
        else:
            # Use LiteLLM for other providers
            return ChatLiteLLM(
                model=f"{provider}/{model}",
                api_key=self._get_api_key(provider)
            )
```

```python
        messages: list[dict[str, Any]],

    ) -> AsyncIterator[dict[str, Any]]:

        ...
```

#### Pattern 3: SDK Feature Detection

```python
def supports_feature(llm: BaseLLM, feature: str) -> bool:
    """Check if LLM supports specific feature."""

    features = {
        "streaming": hasattr(llm, "stream"),
        "tool_calling": hasattr(llm, "invoke") and "tools" in signature,
        "vision": isinstance(llm, ClaudeAgentWrapper) and llm.supports_vision,
        "extended_thinking": isinstance(llm, ClaudeAgentWrapper),
    }

    return features.get(feature, False)
```

## Consequences

### Positive Consequences

1. **Claude-Specific Optimizations**
   - Native Claude tool calling patterns
   - Optimized streaming performance
   - Better error messages and debugging
   - Access to Claude-specific features (extended thinking, vision)

2. **Improved Reliability**
   - SDK-managed retry logic with exponential backoff
   - Automatic reconnection for streaming
   - Better error classification and handling
   - Rate limit awareness

3. **Developer Experience**
   - Type-safe SDK interfaces
   - Comprehensive error types
   - Better documentation (Anthropic's SDK docs)
   - Easier debugging with SDK logging

4. **Performance**
   - Reduced latency for Claude requests (SDK optimizations)
   - Efficient streaming implementation
   - Connection pooling and reuse
   - Automatic request batching (where applicable)

5. **Future-Proof**
   - Access to new Claude features as SDK evolves
   - SDK updates provide instant improvements
   - Alignment with Anthropic's best practices
   - Support for upcoming Claude capabilities

### Negative Consequences

1. **Additional Dependency**
   - `anthropic` package added (~2MB installed size)
   - Version management for SDK updates
   - Potential breaking changes in SDK updates
   - Increased testing surface area

2. **Code Complexity**
   - Dual-path implementation (SDK vs LiteLLM)
   - Abstraction layer overhead
   - Feature detection logic required
   - More configuration options

3. **Learning Curve**
   - Team must understand Claude SDK concepts
   - Different debugging approaches for SDK vs LiteLLM
   - SDK-specific error handling patterns

4. **Migration Overhead**
   - Gradual migration of existing Claude usage
   - Feature flag management during rollout
   - Testing both code paths during transition
   - Documentation updates

### Neutral Consequences

- Backward compatible (existing LiteLLM usage unchanged)
- Optional feature (controlled by feature flag)
- No impact on non-Claude providers

## Alternatives Considered

### 1. Continue with LiteLLM Only

**Pros**:
- Simpler codebase (single provider abstraction)
- No additional dependencies
- Unified interface across all providers
- Easier testing (single code path)

**Cons**:
- Missing Claude-specific optimizations
- Manual retry logic implementation
- No access to Claude SDK features
- Less efficient tool calling

**Why Rejected**: Leaves performance and features on the table when using Claude models

### 2. Replace LiteLLM with Native SDKs

**Pros**:
- Maximum optimization for each provider
- Direct access to all provider features
- Best possible performance

**Cons**:
- Massive code duplication
- Different interfaces per provider
- Difficult to maintain
- Loses multi-provider abstraction benefits

**Why Rejected**: Too much complexity, violates DRY principle

### 3. Use LangChain's ChatAnthropic

**Pros**:
- Already integrates with LangGraph
- LangChain ecosystem integration
- Simpler than dual-path approach

**Cons**:
- LangChain abstraction layer overhead
- Not as optimized as native SDK
- Dependency on LangChain updates
- Less control over low-level SDK features

**Why Rejected**: Adds unnecessary abstraction layer, prefer direct SDK usage

### 4. Fork LiteLLM to Add Claude Optimizations

**Pros**:
- Maintains single provider abstraction
- Could contribute back to LiteLLM
- Unified interface preserved

**Cons**:
- Maintenance burden of fork
- Divergence from upstream LiteLLM
- Delayed updates from LiteLLM improvements
- Difficult to keep in sync

**Why Rejected**: Maintenance burden too high, fork management complex
