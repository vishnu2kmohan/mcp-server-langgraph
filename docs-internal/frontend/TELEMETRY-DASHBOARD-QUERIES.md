# Frontend Telemetry Dashboard Queries

This document provides Grafana/Loki queries for monitoring frontend hook telemetry.
The telemetry is generated by `hookTelemetry.ts` and logs to the console in development.

## Overview

Frontend hooks use `useHookTelemetry` to log:
- **Degradation events**: When hooks fall back to safe defaults
- **Error events**: When WebSocket or API errors occur
- **Retry events**: When retry logic is triggered
- **Backoff events**: When exponential backoff delays occur

## Log Format

All telemetry logs follow this format:
```
[HookName] Event type { context }
```

Examples:
```
[useAISuggestionsWebSocket] Graceful degradation { reason: "missing_session_id", endpoint: "ai_suggestions" }
[useCostTrackingWebSocket] Error occurred { error: "Budget exceeded", endpoint: "cost_tracking" }
[useWebSocketMetricsPush] Exponential backoff { attempt: 2, delayMs: 4000 }
```

## Loki Queries

### Error Rate by Endpoint

Track error frequency across WebSocket endpoints:

```logql
sum by (endpoint) (
  count_over_time(
    {app="studio-frontend"} |~ "Error occurred" | json | endpoint != "" [5m]
  )
)
```

### Degradation Events by Reason

Monitor graceful degradation patterns:

```logql
sum by (reason) (
  count_over_time(
    {app="studio-frontend"} |~ "Graceful degradation" | json | reason != "" [1h]
  )
)
```

### Missing Session ID Errors

Track missing session ID issues (common integration problem):

```logql
count_over_time(
  {app="studio-frontend"} |~ "missing_session_id" [1h]
)
```

### Retry Attempts

Monitor retry behavior:

```logql
{app="studio-frontend"} |~ "Retry attempt" | json
| line_format "{{.hookName}}: attempt {{.attempt}}/{{.maxAttempts}}"
```

### Backoff Delays

Track exponential backoff patterns:

```logql
avg by (hookName) (
  {app="studio-frontend"} |~ "Exponential backoff" | json | unwrap delayMs
)
```

### Hook Health Overview

Get counts of all telemetry events:

```logql
sum by (type) (
  count_over_time(
    {app="studio-frontend"} |~ "\\[use.*WebSocket\\]|\\[useWebSocketMetricsPush\\]" [1h]
  )
)
```

## Grafana Dashboard Panels

### Panel 1: Error Rate Over Time

**Type**: Time series

```logql
sum(
  rate({app="studio-frontend"} |~ "Error occurred" [5m])
)
```

**Title**: Frontend WebSocket Error Rate

### Panel 2: Degradation by Reason (Pie Chart)

**Type**: Pie chart

```logql
sum by (reason) (
  count_over_time(
    {app="studio-frontend"} |~ "Graceful degradation" | json [24h]
  )
)
```

**Title**: Degradation Reasons (24h)

### Panel 3: Endpoint Health Table

**Type**: Table

```logql
sum by (endpoint) (
  count_over_time(
    {app="studio-frontend"} |~ "Error occurred" | json [1h]
  )
)
```

**Title**: Errors by Endpoint (1h)

### Panel 4: Retry Success Rate

**Type**: Stat

```logql
# Calculate retry success rate
# (total attempts - failures) / total attempts * 100
```

**Title**: Retry Success Rate

## Alerting Rules

### High Error Rate Alert

```yaml
alert: FrontendWebSocketHighErrorRate
expr: |
  sum(rate({app="studio-frontend"} |~ "Error occurred" [5m])) > 0.1
for: 5m
labels:
  severity: warning
annotations:
  summary: High frontend WebSocket error rate
  description: Frontend is experiencing elevated error rates
```

### Frequent Degradation Alert

```yaml
alert: FrontendFrequentDegradation
expr: |
  sum(count_over_time({app="studio-frontend"} |~ "Graceful degradation" [5m])) > 50
for: 10m
labels:
  severity: warning
annotations:
  summary: Frequent frontend degradation events
  description: Frontend is frequently falling back to degraded behavior
```

### Retry Exhaustion Alert

```yaml
alert: FrontendRetryExhaustion
expr: |
  sum(count_over_time({app="studio-frontend"} |~ "retriesExhausted.*true" [5m])) > 5
for: 5m
labels:
  severity: critical
annotations:
  summary: Frontend retry exhaustion
  description: Frontend is exhausting retries - backend connectivity issue likely
```

## Production Setup

For production, configure the frontend to send logs to a centralized logging system:

1. **Option A: Console transport to Grafana Agent**
   - Grafana Agent scrapes container stdout
   - Logs flow to Loki automatically

2. **Option B: Direct OTLP export**
   - Configure OpenTelemetry browser SDK
   - Export logs via OTLP to collector

3. **Option C: Custom log shipper**
   - Implement custom transport in `devLogger.ts`
   - Send logs to backend endpoint for forwarding
